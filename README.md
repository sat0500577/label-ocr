# 라벨 OCR

상품 라벨 사진에서 **제품명/색상**(예: `HP딘버일자/그레이`)을 뽑아내는 웹앱.
안드로이드 Chrome과 아이폰 Safari에서 같은 주소로 사용한다.

**https://sat0500577.github.io/label-ocr/**

아이폰은 Safari의 공유 메뉴 → **홈 화면에 추가**, 안드로이드는 Chrome 메뉴 →
**홈 화면에 추가 / 앱 설치**로 설치한다. 앱스토어에 등록하는 네이티브 앱은 아니다.
처음에는 인터넷에 연결한 상태에서 **준비됐습니다**가 표시될 때까지 기다린다.
엔진·모델과 화면 파일을 캐시한 뒤에는 오프라인으로 다시 열고 인식할 수 있다.
브라우저가 사이트 데이터를 지우거나 저장 공간을 제한하면 인터넷에 연결해 다시 준비해야 한다.

## 사용 방법

1. **사진 찍기** 또는 **앨범에서 선택**으로 라벨을 불러온다.
2. 자동 인식 결과를 확인한다. 기본 결과는 `제품명/색상`이다.
3. 잘 읽히지 않으면 미리보기에서 제품명·색상이 있는 부분을 드래그한다.
4. 결과를 직접 수정하고 **복사**, **공유** 또는 **파일 저장**을 누른다.
   파일 저장은 한글을 보존하는 UTF-8 `.txt` 파일을 만든다. 공유 버튼은 브라우저가 지원할 때 표시된다.

인식 중에는 다른 사진 선택과 영역 변경을 잠시 막아 사진과 결과가 섞이지 않게 한다.
사진은 서버로 전송하지 않으며 결과를 자동으로 외부에 저장하지 않는다.
카메라가 열리지 않는 앱 내 브라우저에서는 Safari 또는 Chrome으로 주소를 다시 연다.
브라우저가 읽을 수 없는 HEIC 등은 JPG·PNG로 바꾸거나 카메라로 다시 촬영한다.

## 어떻게 동작하나

서버가 없다. 사진 촬영·글자 인식·추출이 전부 브라우저 안에서 끝나고, 사진은 어디로도 전송되지 않는다.

1. 촬영한 사진을 긴 변 2400px까지 줄이고 EXIF 회전을 바로잡은 뒤, 가장자리의 **단색 여백을
   잘라낸다**(`trimUniformBorder`). 카메라나 화면 캡처가 붙이는 검은 띠가 남아 있으면
   Tesseract의 이진화 기준이 그쪽으로 쏠려 라벨 글자를 통째로 못 읽는다(실측 확인).
   단, 글자 획이 잘리지 않게 원래 사진의 여백 12px를 남긴다. 터치로 고른 영역은 정수 픽셀로 맞춘다.
   큰 원본의 축소와 OCR 입력 확대는 `ocr-image.js`의 공통 Mitchell bicubic 필터로 처리한다.
   원본은 32행씩 읽고 필요한 중간 행만 보관한다. 투명한 사진은 흰 배경에 합성한다.
   브라우저별 Canvas 고품질 필터 차이로 같은 원본의 결과가 달라지는 문제를 줄인다.
   글자 주변의 작은 여백은 [Tesseract 품질 가이드](https://tesseract-ocr.github.io/tessdoc/ImproveQuality.html#borders)에서도 권장한다.
2. **사진 방향을 맞춘다.** 옆으로 누운 사진은 Tesseract가 한 글자도 못 읽는다.
   바코드 줄무늬의 촘촘함을 가로·세로로 각각 재서, 세로가 더 촘촘하면 누운 사진으로 본다.
   바코드가 오른쪽에 있으면 시계 방향, 왼쪽이면 반시계 방향으로 돌린다. 이 짐작이 빗나가면
   나머지 방향도 읽어 보고 **'확실한 한글이 몇 자인지'로 고른다**. 짝(`/`)이 나왔는지로
   고르면 안 된다. 쓰레기 글자끼리도 짝은 만들어진다(실측 확인).
3. **바코드를 지운다**(`suppressBarcode`). 바코드가 화면에 있으면 Tesseract의 레이아웃
   분석이 무너져 글자를 **아예 못 읽는다**(실측 확인).
   - 밝기 기준은 **행마다 따로** 잡는다. 사진 전체에 하나를 쓰면 배경이 넓거나 조명이
     고르지 않은 사진에서 바코드 구조가 통째로 안 보인다.
   - 판정은 `전환 횟수 / 글자가 놓인 구간의 폭`. 화면 폭으로 나누면 라벨이 작게 찍힌
     사진에서 바코드를 놓친다. 가장 촘촘한 행의 60%를 기준선으로 삼고, 그런 행이
     높이의 5% 넘게 이어질 때만 바코드로 본다.
   - 덮는 색은 반드시 사진의 중간 밝기여야 한다. 흰색으로 덮으면 이진화 기준이 밀려
     나머지 글자까지 통째로 사라진다.
4. 인식 폭이 최소 1600px가 되도록 **확대**한다. 절대 축소하지 않는다. 라벨이 작게 찍힌
   사진을 줄이면 글자가 뭉개져 한 글자도 못 읽는다. 그러고도 글자 줄 높이가 42px 미만이면
   2배로 키워 한 번 더 읽는다. 이어서 Tesseract.js로 두 번 읽는다.
   페이지 분할은 **PSM 11(희소 텍스트)**. 라벨처럼 글자가 흩어져 있을 때 기본 모드보다 훨씬 잘 찾는다.
   한국어 모델과 영어 모델을 따로 돌린다. `kor+eng`로 한 번에 돌리면 "HP딘버일자"처럼
   영문 뒤 한글을 영문 단어로 오인해 깨뜨린다.
5. `labelFormat()`이 필요한 줄만 고른다.
   - 줄 묶기는 **Tesseract가 만든 줄 구조를 그대로 쓴다**. y좌표로 직접 묶으면 기울어진
     라벨에서 오른쪽 분류명이 왼쪽 둘째 줄과 섞인다(실측 확인).
   - 신뢰도 70 이상인 글자가 2자 미만인 줄은 포장지 잔글씨로 보고 버린다.
   - 줄 높이 중앙값의 **40%** 미만인 줄도 버린다. 이 기준을 빡빡하게 잡으면 안 된다.
     '그레이'처럼 받침·윗글자가 없는 줄은 같은 글자 크기라도 줄 상자가 30% 가까이 낮게
     잡혀, 60%로 자르면 색상 줄이 통째로 사라진다(실측 확인).
   - **제품명·색상은 같은 열에 위아래로 붙어 있는 '짝'**이다. 그 짝이 되는 두 줄을 먼저 찾는다.
     이름 줄을 못 읽었을 때 오른쪽 분류명(헤어집게)을 제품명으로 집는 것을 막는다.
   - 줄 안에서 글자를 끊는 간격은 **그 줄 자신의 높이**로 잰다. 여러 줄의 중앙값을 쓰면
     잔글씨 줄이 섞여 기준이 작아지고 제품명이 중간에서 잘린다(`H딘버`, 실측 확인).
   - 한국어 모델은 앞머리 영문 'H'를 '너'로 **신뢰도 90**에 읽는다. 신뢰도로는 못 거른다.
     진짜 영문이면 두 모델이 같은 잉크를 보므로 **상자 양끝이 거의 일치**하고, 한글을 영문으로
     잘못 읽은 경우는 눈에 띄게 어긋난다('유'와 'F'가 40px 차이). 그 차이로 가른다. 다만 이 판정은
     줄 맨 앞에서 연속되는 두 글자까지만 적용한다. 영어 모델은 진짜 한글도 알파벳으로
     자신 있게 읽어서, 제한이 없으면 제품명 전체가 영문으로 바뀐다(실측 확인).
   - 제품명 = 그 기준점부터 줄 끝까지(영문+완성형 한글만, 숫자·기호·낱자모 제거).
     색상 = 아래 줄(완성형 한글만).

검증한 촬영 조건: 원본, 흐림, 어두움, 기울어짐(추가 6도), 멀리서 찍어 라벨이 작은 경우,
넓은 프레임, 위아래 검은 여백, 90·180·270도 회전. 라벨 두 종류로 모두 정확히 나온다
(`HP딘버일자/그레이`, `R유광하이/그린`).

## 속도

인식 속도는 기기의 성능과 사진 크기에 따라 달라진다. 기존 개발 환경에서는 인식 호출 한 번에
약 1초의 고정 비용이 관찰돼 불필요한 호출을 줄이는 방식으로 최적화했다.

- **앱을 열자마자 엔진·모델을 미리 올린다.** 준비 도중 사진을 골라도 같은 초기화 작업을
  기다려 중복 워커가 생기지 않는다. 첫 다운로드 시간은 네트워크와 기기에 따라 달라진다.
- **한글만으로 이미 제품명·색상 짝이 나왔으면 확대 재시도를 건너뛴다.** 인식 한 번을 통째로 아낀다.
- **영문도 한글과 같은 크기로 읽는다.** 별도로 줄이면 기울어진 라벨의 `HP`가 `Pm`으로
  바뀌는 회귀가 확인됐다. 결과 좌표도 두 패스에서 그대로 비교한다.
- **누운 사진은 바코드 방향으로 각도를 짚어 한 번에 맞춘다.** 네 방향을 다 읽으면 15초가
  걸리는데, 짚어서 맞히면 3.7초다.

`OCR_TARGET_W`를 낮추는 것은 역효과다. 글자가 작아져 확대 재시도가 걸리고, 인식 횟수가 늘어
오히려 느려지면서 정확도까지 떨어진다(1300으로 낮췄더니 8초, HP가 H로 줄어듦).

자동 인식이 빗나가면 미리보기에서 글자 부분을 끌어 선택해 그 영역만 인식시킬 수 있다.
"한글만"·"전체" 모드도 있어 라벨이 아닌 사진에도 쓸 수 있다.

## 파일

```
index.html          화면·OCR 호출·제품명/색상 추출 규칙
ocr-image.js        브라우저 공통 OCR 이미지 확대 필터
sw.js               경로별 오프라인 캐시. 화면과 vendor 캐시를 분리
manifest.json       홈 화면 추가용 앱 정보
icon.png            앱 아이콘
sample-label.png    테스트용 합성 라벨 (HP딘버일자/그레이)
sample-label2.png   테스트용 합성 라벨 (R유광하이/그린)
vendor/             Tesseract.js 엔진·wasm 코어·kor/eng 모델
scripts/serve.cjs    로컬 테스트 서버
tests/              실제 OCR·모바일 사용 흐름·오프라인·오류 복구 테스트
```

`index.html` 또는 `ocr-image.js`를 고쳐 다시 올릴 때는 `sw.js`의 `shell-v9` 버전을 올린다.
엔진·모델이 변경될 때만 `vendor-v1` 버전을 올린다. 다른 GitHub Pages 앱의 캐시는 삭제하지 않는다.

## 로컬 실행과 검증

Node.js 22 이상에서:

```sh
npm ci
npm run dev
# http://127.0.0.1:4173
```

앱 자체는 빌드가 필요 없는 정적 사이트다. `npm ci`는 개발용 테스트 도구를 설치한다.
HTML을 파일로 직접 열면 Web Worker·오프라인 기능이 제한되므로 로컬 서버 또는 HTTPS를 사용한다.

```sh
npx playwright install chromium webkit
npm test
```

Chromium(Pixel 7 화면 설정)과 WebKit(iPhone 13 화면 설정)에서 두 기본 라벨 및 변형을 검사한다.
두 라벨 각각 원본, 흐림, 어두움, 6도 기울기, 먼 거리, 넓은 프레임, 검은 여백, 90·180·270도 회전을 사용한다.
모바일 파일 선택, 결과 편집, UTF-8 다운로드, 잘못된 파일 복구, 영역 선택 취소,
워커 초기화 경합·실패 재시도, 서버 종료 후 오프라인 새로고침도 검사한다.
변형 PNG는 한 번만 생성해 두 브라우저에 동일한 파일을 입력한다.
브라우저 에뮬레이션이며 실제 휴대폰 카메라·공유 메뉴·홈 화면 설치까지 검증한 것은 아니다.
실사용 정확도는 실제 촬영한 라벨로 추가 확인해야 한다. 예제 통과율을 일반적인 정확도로 해석하지 않는다.
