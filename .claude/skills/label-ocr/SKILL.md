# 라벨 OCR 디버깅

`index.html` 하나에 화면·OCR 호출·추출 규칙이 다 들어 있다. 서버는 없다.

## 먼저 할 일: 재현

**화면 캡처로 짐작해서 고치지 마라.** 캡처는 화면 크기로 줄어든 이미지라 실제 사진보다
흐리다. 내 환경에서는 통과하는데 폰에서는 실패하는 일이 반복된다. 원본 사진 파일을 받아라.

재현 방법: 사진을 `web/` 아래에 두고 로컬 서버를 띄운 뒤 브라우저 콘솔에서 돌린다.

```js
const b = await fetch('/사진.png').then(r => r.blob());
await window.hangulOcr.handleFile(new File([b], 'x.png', { type: 'image/png' }));
document.getElementById('result').value
```

내부를 볼 때는 `window.hangulOcr.lastData`(kor·eng 패스 결과)와
`window.hangulOcr.buildOcrCanvas(1, 0)`(전처리 결과·바코드 밴드·회전 판정값)을 본다.
줄 단위로 보려면 `lastData.kor.lines` 안의 `words`에서 `text`·`conf`·`x0`·`x1`을 찍어 본다.

## 이미 확인한 함정 (다시 밟지 마라)

모두 실측으로 확인한 것이다. "그럴 리 없다"고 생각되면 위 방법으로 직접 재현해 보라.

### 이미지 전처리

- **바코드가 화면에 있으면 글자를 아예 못 읽는다.** 레이아웃 분석이 무너진다.
  바코드만 덮으면 같은 사진이 신뢰도 90대로 읽힌다.
- **덮는 색을 흰색으로 하면 인식 결과가 0글자가 된다.** 이진화 기준이 밀린다.
  반드시 사진의 중간 밝기로 덮어라.
- **위아래 검은 여백(레터박스)도 같은 이유로 치명적이다.** 여백만 잘라내면 정상이 된다.
- **밝기 기준은 행마다 따로 잡아라.** 사진 전체에 하나를 쓰면 배경이 넓은 사진에서
  바코드 구조가 통째로 안 보인다.
- **바코드 판정은 화면 폭이 아니라 글자가 놓인 구간 폭으로 나눠라.** 화면 폭으로 재면
  라벨이 작게 찍힌 사진에서 놓친다.
- **절대 축소하지 마라.** 라벨이 작게 찍힌 사진을 줄이면 한 글자도 못 읽는다.

### 인식 호출

- **`kor+eng`를 한 번에 돌리면 안 된다.** 영문 뒤 한글을 영문 단어로 오인해 깨뜨린다.
  한국어와 영어를 따로 돌리고 결과를 합쳐라.
- **PSM은 11(희소 텍스트).** 라벨처럼 글자가 흩어져 있을 때 기본 모드보다 훨씬 잘 찾는다.
- **인식 영역을 잘라내면 결과가 나빠질 수 있다.** 명암 기준이 달라진다. 줄이는 것은 되지만
  잘라내는 것은 위험하다.
- **옆으로 누운 사진은 한 글자도 못 읽는다.** 바코드 줄무늬의 촘촘함을 가로·세로로 재서
  방향을 짚어라. 방향 선택은 '확실한 한글이 몇 자인지'로 한다. 짝(`/`)이 나왔는지로 고르면
  쓰레기 글자끼리도 짝을 이뤄 잘못 고른다.

### 줄·글자 고르기

- **줄 묶기는 Tesseract가 만든 줄 구조를 그대로 써라.** y좌표로 직접 묶으면 기울어진
  라벨에서 오른쪽 분류명이 왼쪽 둘째 줄과 섞인다.
- **줄 높이 기준을 빡빡하게 잡지 마라.** '그레이'처럼 받침·윗글자가 없는 줄은 같은 글자
  크기라도 줄 상자가 30% 가까이 낮게 잡힌다. 중앙값의 60%로 자르면 색상 줄이 사라진다.
- **줄 안에서 글자를 끊는 간격은 그 줄 자신의 높이로 재라.** 여러 줄의 중앙값을 쓰면
  잔글씨 줄이 섞여 기준이 작아지고 제품명이 중간에서 잘린다.
- **제품명·색상은 같은 열에 위아래로 붙은 짝으로 찾아라.** 이름 줄을 못 읽었을 때
  오른쪽 분류명을 제품명으로 집는 것을 막는다.

### 앞머리 영문(HP·R 등)

여기가 가장 까다롭다. 한국어 모델은 `H`를 `너`로 **신뢰도 90**에 읽는다.

- **신뢰도로는 못 가른다.** 진짜 영문이든 진짜 한글이든 한국어 쪽 신뢰도가 똑같이 낮게
  (17 같은 값) 나오는 경우가 있다.
- **상자 양끝이 거의 일치하는지로 가른다.** 진짜 영문이면 두 모델이 같은 잉크를 보므로
  양끝이 맞고, 한글을 영문으로 잘못 읽은 경우는 눈에 띄게 어긋난다(`유`와 `F`가 40px 차이).
  허용 오차는 글자 폭의 0.45배. 이 값은 좁혀도 넓혀도 한쪽이 깨지는 좁은 구간이다.
- **이 판정은 줄 맨 앞 연속 두 글자까지만 적용하라.** 영어 모델은 진짜 한글도 알파벳으로
  자신 있게 읽어서, 제한이 없으면 제품명 전체가 영문으로 바뀐다.
- **접두어 자를 위치는 상자 끝이 아니라 중심으로 재라.** 끝으로 재면 옆 글자와 몇 픽셀
  겹쳤다는 이유로 멀쩡한 `P`가 빠진다.

### 속도

- **인식 한 번에 1초 남짓의 고정 비용이 붙는다. 이미지 크기와 무관하다**(300x120으로 줄여도
  1.04초). 그래서 관건은 크기가 아니라 **호출 횟수**다.
- **`OCR_TARGET_W`를 낮추는 것은 역효과다.** 글자가 작아져 확대 재시도가 걸리고 호출이 늘어
  오히려 느려지면서 정확도까지 떨어진다.
- 엔진·모델 준비에만 5~6초가 걸린다. 앱을 열자마자 미리 올려 둔다.

## 검증

고칠 때마다 아래 조건을 **전부** 다시 돌려라. 한 곳을 고치면 다른 곳이 깨지는 일이 잦다.

원본, 흐림, 어두움, 기울어짐(6도), 멀리서 찍어 라벨이 작은 경우, 넓은 프레임,
위아래 검은 여백, 90·180·270도 회전. 라벨 두 종류(`sample-label.png`,
`sample-label2.png`)로 각각 확인한다. 기대값은 `HP딘버일자/그레이`, `R유광하이/그린`.

변형 이미지는 원본에 흐림·밝기·회전을 입혀 만든다. 단색으로 여백을 채우지 마라. 실제
사진에는 없는 조건이라 엉뚱한 실패를 만든다. 배경은 원본을 흐리게 깔고 잡음을 섞어 쓴다.

## 고칠 수 없는 것

글자 인식 단계에서 이미 틀린 것은 뒤에서 규칙으로 못 고친다. 흐린 사진에서 `유`가 `F`로,
`이`가 `0`으로 읽히는 것이 그렇다. 이때 할 수 있는 것은 둘뿐이다.

1. 사용자가 미리보기에서 글자 부분만 끌어 선택하게 한다(이미 있는 기능).
2. 더 나은 인식 엔진으로 바꾼다. Tesseract보다 한국어를 잘 읽는 것은
   iOS Live Text, Google ML Kit, 네이버 CLOVA OCR 등이다.

규칙을 더 복잡하게 만들어 특정 사진 하나를 맞히려 들지 마라. 다른 사진이 깨진다.
